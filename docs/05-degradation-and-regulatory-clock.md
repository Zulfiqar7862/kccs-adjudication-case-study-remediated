# Notification policy and degradation

Implemented: separate applicability, policy resolution, receipt evidence and assessment; original alert anchor; no default72h; no breach finding for an unknown jurisdiction. A supplied numeric extract window may be compared with the supplied receipt offset as a source consistency observation. It cannot qualify the law. Explicit nonreportable rows are NOT_APPLICABLE; conflicting receipt facts remain an input conflict. Missing receipt is unknown, not assumed absent; future receipts are not already observed at earlier as-at times.

Brief Section4/tab13 facts:72hours for two EU markets (not all Europe), Brazil5calendar days, India15days for notifiable products, one unidentified US state nextbusinessday. Current resolver accepts explicit `EU_72H_MARKET_CONFIRMED`, `BR`, `IN_NOTIFIABLE` jurisdiction tags; national fixed-hour intervals are provisional mappings and are not a complete localized calendar-day policy qualification. The actual extract does not establish these legal bindings. US policy must be explicitly passed with timezone, business-calendar ID, holidays and cutoff; no state/calendar is guessed. Synthetic tests demonstrate the calendar algorithm, not a legally approved state programme. Brazil local calendar-day/DST semantics remain a qualification gap.

A reopen inherits the original assessment; there is no independent clock reset or pause. Do not call historical source-window lateness a new legal breach. A disposition can occur later than notification; source signing time and notification receipt are distinct.

Target degradation (not live services): if telemetry/ERP/documents fail, retain originals, flag staleness and block unsupported signing; notify independently using the original alert. If model fails, remain deterministic/manual. If audit persistence fails, block new signatures; if notification scheduler fails, escalate through a separately tested contingency. Buffer/retry/monitoring/recovery are design requirements, not behavior of this batch CLI.
